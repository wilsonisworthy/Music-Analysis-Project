MUSIC ANALYSIS PROJECT — SUMMARY
==================================
(Everything built so far, in the order it happened.)


1. THE ROUTER (main.py)
------------------------
A terminal menu that browses the subprojects/ folder tree and lets you run
whatever script you land on, so this can grow into a multi-subproject
codebase without a growing pile of "which script do I run again?" tribal
knowledge.

- Arrow-key navigation (Up/Down or w/s, Enter to select, Left/Backspace to
  go back, Esc/q to quit). The selected item is highlighted with reverse
  video (ANSI escape codes).
- Falls back to a plain numbered-input menu automatically when stdin isn't
  a real terminal, or when running under Git Bash/MSYS.
  NITTY GRITTY: this fallback isn't just for piped/non-interactive use.
  Git Bash's mintty pty reports isatty()==True even though it doesn't give
  Windows' msvcrt module a real console handle, so arrow-key reads would
  silently hang forever. Caught this by actually reproducing the hang,
  then fixed it by detecting the MSYSTEM environment variable and routing
  to the plain fallback whenever it's set.
- Screen clears before every menu render in both modes, so the terminal
  doesn't fill up with stale menus as you navigate.
- Folder/file discovery is fully automatic: ANY .py file directly inside a
  subprojects/ folder becomes a runnable menu entry (not just a hardcoded
  "main.py"). A file opts out of the menu by prefixing its name with "."
  or "_" (e.g. _shared.py), or by adding a "# router:skip" comment in its
  first ~20 lines. Same underscore/dot rule applies to folders.
- Each script runs as its own subprocess (python <script>.py), with its
  cwd set to its own folder, so subprojects stay isolated from each other.
- UPDATE (2026-08-27): added a multi-select menu (choose_multi(), next to
  the original single-select choose()) -- Space toggles the highlighted
  item, 'a' toggles all, Enter confirms; the plain fallback accepts
  comma-separated numbers/ranges ("1,3,5-8") or "all". Built so the
  compare/ subproject (section 6) could let the user pick many recordings
  at once instead of one at a time.


2. AUDIO ANALYSIS SCRIPTS (subprojects/statistic_from_audio/)
----------------------------------------------------------------
Two analysis tools, each in its own folder (harmonics/, amplitude/),
following the router's one-script-per-folder convention. Both were
originally under a folder called audio_analysis/ before being reorganized
into statistic_from_audio/ to match folders the user had already started.

harmonics/main.py — timbre-over-time analysis (rewritten; see history below)
  - CURRENT VERSION: deliberately does NOT report a fundamental frequency
    or note name at all (the user pointed out the filename already tells
    you the note). Instead it answers "how does the tone color change
    while the note plays?" via an STFT (a Fourier transform computed
    repeatedly over sliding time windows = a spectrogram) and a per-frame
    spectral centroid ("brightness" — the amplitude-weighted average
    frequency; higher means more energy in the upper harmonics). Output:
    a spectrogram plot with the brightness curve overlaid, a separate
    brightness-vs-time plot, and a one-line printed verdict (brighter /
    darker / roughly constant, with a fitted percent change).
  - THE BUG CAUGHT HERE: the first version of this compared brightness in
    the first 2%-of-peak-energy window vs a hardcoded threshold and found
    every note "got brighter" by up to +236%. That was fake. As a real
    note's signal decays toward silence, a flat background noise floor
    (room/mic noise) becomes a bigger share of each frame's total energy;
    since that floor isn't bass-weighted the way a piano tone is, it
    drags the measured centroid upward as the real signal fades out —
    the "brightening" was mostly the note fading into noise, not the
    note's actual timbre changing.
  - THE FIX: gate frames on SNR above a measured noise floor (taken from
    the silence just before each note's attack) instead of a fixed
    fraction of peak energy, and require 15dB above that floor before
    trusting a frame's centroid. Also switched the trend calculation from
    a noisy "average the first/last 10%" comparison to a proper linear
    fit across every valid frame, which is far less sensitive to a few
    noisy points at either edge.
  - HONEST RESULT AFTER THE FIX: even with the noise-floor bug gone, 6 of
    8 test notes still measurably brighten over their reliably-audible
    duration (2 stay flat). That looks backwards from the common "notes
    get warmer as they decay" intuition, but that intuition is really
    about the long, low-SNR decay tail this fix now correctly excludes as
    unmeasurable, not the portion actually being measured. Reported as
    real data rather than forced to match the intuition. Not fully
    explained yet — worth a literature check on piano transient behavior
    if pursued further.
  - EARLIER VERSION (replaced, kept here since the debugging process is
    itself informative): originally reported a single estimated
    fundamental frequency + up to 10 harmonics from one whole-clip FFT.
    Had its own bug — picking the single loudest bin as "the
    fundamental" fails on real piano notes because the 2nd harmonic is
    often louder than the true fundamental, causing consistent
    one-octave-too-high errors. Was fixed with a Harmonic Product
    Spectrum (multiply the spectrum by itself decimated by 2x, 3x, ...,
    so the true fundamental's bin gets reinforced by every harmonic
    while a false octave-up candidate only lines up with every other
    one), tuned to 3 harmonics instead of the textbook 5 (piano partials
    drift sharp of exact integer multiples higher up, so including more
    of them added noise). That approach was abandoned entirely once the
    user clarified they didn't want fundamental/note detection at all —
    it's superseded, not merged with the current version.

amplitude/main.py — amplitude envelope analysis
  - Computes an RMS envelope in 10ms frames and estimates the note's
    shape from it: attack (silence -> peak) and decay (peak -> the level
    dropping back below 5% of the peak). Plots the envelope with both
    boundaries marked.
  - NITTY GRITTY: originally modeled as a full ADSR (attack/decay/
    sustain/release), like a synthesizer envelope. Removed the sustain
    and release stages entirely, on purpose — a piano note is a struck,
    continuously-decaying sound with no true sustain plateau the way a
    bowed or wind instrument has one. Forcing an ADSR model onto a piano
    note means guessing at a plateau that isn't really there. Attack +
    decay is what actually matches the physics.

_shared.py (duplicated identically into both harmonics/ and amplitude/,
matching the project's existing pattern of each script folder being
self-contained)
  - Loads a WAV file as float64 mono samples, downmixing stereo and
    normalizing integer PCM to [-1, 1].
  - COOL THING: instead of asking the user to type a file path, it
    reaches back into the project root and imports choose() directly out
    of main.py — the exact same arrow-key/numbered menu the router itself
    uses — so picking a WAV file feels identical to picking a subproject.
    It finds the project root by walking up the directory tree looking
    for a folder that has both main.py and subprojects/ in it, so it
    isn't hardcoded to a specific folder depth.
  - UPDATED (2026-08-27, first pass): scanned TWO folders (Audio
    Recordings/ and Sample Recordings/, both directly at the project
    root) and merged their contents into one flat picker list, each
    entry labeled "<folder>/<filename>".
  - UPDATED AGAIN (2026-08-27, same day): the user nested both of those
    under one parent, Recordings/, and asked for "the folder structure
    method" instead of a flat merged list. select_wav()/select_wavs()
    were rewritten to browse Recordings/ the same folder-by-folder way
    the router (main.py) browses subprojects/ -- descend into
    subfolders via the arrow-key/plain menu, land on files. For multi-
    select specifically, since you can't cleanly mix "descend into a
    folder" actions with per-item checkboxes in one menu, navigation
    stays single-select until you reach a folder that actually has WAV
    files in it; that folder gets an extra "[ Select from the N file(s)
    here ]" menu entry which switches to choose_multi() scoped to just
    that folder. So cross-folder multi-select (picking some files from
    Sample Recordings/ AND some from Audio Recordings/ in one go) isn't
    supported -- you multi-select within one folder at a time. Nothing
    asked for that yet; worth revisiting if it comes up.

4. TEST DATA, ROUND 1 — MAESTRO DATASET (superseded, see section 5)
------------------------------------------------------------------------
8 real piano notes were first pulled from Google Magenta's MAESTRO v3.0.0
dataset. These have since been replaced (section 5) because MAESTRO is
full multi-note performances, not isolated single notes, and heavy
sustain-pedal use in the source recording caused real acoustic bleed
between notes. Keeping this section as a record of what was tried and
learned.

  maestro_01_G2.wav    maestro_05_A#4.wav
  maestro_02_D4.wav    maestro_06_D#5.wav
  maestro_03_D#4.wav   maestro_07_B3.wav
  maestro_04_D4.wav    maestro_08_G4.wav

Source performance: J.S. Bach, Prelude and Fugue in G Minor (WTC II,
BWV 885), a 2011 recording — the single shortest recording in the entire
MAESTRO v3.0.0 dataset (45 seconds), chosen specifically to keep the
download small.

COOL THING / THE NITTY GRITTY: MAESTRO doesn't host individual audio files
you can just download — the only options are one 108GB zip containing
every performance, or TensorFlow TFRecord shards. Downloading 108GB for
one 45-second clip wasn't happening. Instead, this used the fact that (a)
ZIP files store a central directory that lets you look up any single
file's exact byte range without reading the rest of the archive, and (b)
Google Cloud Storage supports HTTP range requests. Using the `remotezip`
library, the target audio + MIDI files were extracted directly out of the
108GB archive in about 2.5 seconds, touching only the ~8MB actually
needed.

The MIDI file (aligned to the audio, sample-accurate) was then parsed with
`mido` to find note onset/offset times, rank notes by how much clear time
exists before the next note starts, and slice out the 8 most isolated
ones as individual WAV clips (~50ms of pre-roll before each onset, capped
at 2 seconds).

CONCLUSION FROM TESTING AGAINST THIS DATA: running harmonics/main.py
against all 8 notes and comparing against their known MIDI pitch, 6 of 8
fundamentals were detected correctly after the HPS fix. The 2 that still
fail (A#4, D#5) aren't a tunable-parameter problem — they fail at every
harmonic-count setting tried. The real cause: this recording uses heavy
sustain pedal (one note in the piece rings for over 7 seconds), so other
undamped strings resonate in sympathy and leak real acoustic energy into
the clip that has nothing to do with the target note's own harmonic
series. No amount of spectral-domain tuning fixes that — it would need a
pitch tracker that also knows the note's onset/duration, or accepting
that pedaled multi-note recordings are inherently messier than isolated
single-note samples.

The user clarified the actual test target is isolated single piano notes,
not full pedaled performances — so MAESTRO was the wrong kind of dataset
for this project, regardless of the extraction trick working perfectly.


5. TEST DATA, ROUND 2 — UNIVERSITY OF IOWA SINGLE NOTES (current)
-----------------------------------------------------------------------
The MAESTRO clips were fully replaced with genuinely isolated single
piano notes — no pedal, no other notes overlapping, no performance
context at all. Started with 8 (C and G across octaves 2-5), then
expanded to the full chromatic set: all 12 notes across 4 octaves
(2 through 5), 48 files total, piano_single_<note><octave>.wav
(e.g. piano_single_C2.wav ... piano_single_B5.wav, flats spelled as
Db/Eb/Gb/Ab/Bb to match the source archive's naming).

Source: the University of Iowa Electronic Music Studios instrument
sample archive (theremin.music.uiowa.edu) — a long-standing, freely
downloadable set of single-note instrument recordings used widely in
audio research. Each note was recorded in isolation specifically for
sampling purposes. (The Kaggle "Piano Recordings Dataset" cited earlier
would have been a more direct match, but Kaggle requires an account + API
token to download even public datasets, which wasn't available in this
session — Iowa's archive needs no login at all.)

UPDATE (2026-08-29): expanded from mezzo-forte-only to all three dynamic
levels Iowa records piano at -- pp (pianissimo), mf (mezzo-forte), ff
(fortissimo) -- same 48 notes at each, 144 files total. Goal: correlate
strike force/speed with attack time, decay time, and brightness trend,
working toward fitting an equation that predicts note properties from
input force. Laid out as subfolders `Recordings/Sample Recordings/pp/`,
`mf/`, `ff/`, each containing the same `piano_single_<note><octave>.wav`
naming as before (existing mf files were moved in, not re-downloaded).
Downloaded via `Piano.<dyn>.<note><octave>.aiff` under Iowa's
`sound files/MIS/Piano_Other/piano/` path, same AIFF->WAV conversion and
3%-of-peak RMS trim as the original import (buffer 0.3s, capped at 6s).
No importer script was kept in the repo -- consistent with the original
mf-only import, this was a one-off script run from the scratchpad and
discarded, not a permanent subproject.

UPDATE (2026-08-29, same day): the cross-dynamic gap above was closed.
`_shared.py`'s select_wavs() now detects when a folder's immediate
subfolders each hold same-named WAV files (a `_group_wavs_by_subdir()`
helper) and, when that's true, adds an extra menu entry --
"[ Select notes across ff, mf, pp here ]" -- generic, not hardcoded to
those three names, so it'll pick up whatever sibling folder names exist.
Picking a note there pulls it from every sibling folder at once instead of
running compare three separate times. compare/main.py disambiguates same-
named rows with their parent folder (e.g. "C4 (pp)" / "C4 (mf)" /
"C4 (ff)") and sorts them together, softest-to-loudest (a DYNAMIC_ORDER
lookup: pp<p<mp<mf<f<ff, unrecognized names sort after, alphabetically).
Verified end-to-end (headless, mocked choose/choose_multi): selecting A2
and C4 across all three dynamics in one run produced a correctly grouped,
correctly labeled table, e.g. A2's attack time climbed 0.23s (pp) -> 0.46s
(mf) -> 0.64s (ff) -- a real, visible force-vs-attack-time trend, exactly
the kind of relationship the user wants to eventually fit an equation to.

Still true: a batch script dumping all 144 files' attack/decay/brightness
into one CSV would be a better fit than eyeballing compare's table once
the user actually starts fitting a real force -> property equation --
not built yet, only build it if asked.

NITTY GRITTY: the raw files are AIFF format, not WAV, and are extremely
long — around 13 to 74 seconds each, mostly natural decay tail trailing
off toward silence. Converted to WAV with the `soundfile` library, and
trimmed each note individually: computed a quick RMS envelope, found
where the level drops below 3% of the peak, and cut there plus a small
buffer (capped at 6 seconds). Final clips range from about 1.5s (fast-
decaying upper-register notes) to 6.9s (low notes, which naturally ring
longer) — that spread by itself is a real, physically-correct result:
lower piano strings sustain audibly much longer than higher ones. All
48 files were batch-run through both analysis scripts afterward with
zero crashes.

CONCLUSION FROM TESTING AGAINST THIS DATA (against the first 8 notes,
back when harmonics/main.py still reported a fundamental frequency --
see section 2, that whole approach has since been replaced and this
finding no longer applies to the current script, kept here as history):
6 of 8 fundamentals detected correctly, same score as the MAESTRO round,
but with a different and more informative failure pattern — both
failures (C2, G2) were octave errors on the two *lowest* notes
specifically, not scattered across the range. That pointed at a known
phenomenon: on a real piano, the true fundamental of a low bass string
is often physically weaker than its own upper harmonics (a soundboard/
string-coupling effect), which can outvote even an octave-error-
resistant detector in the bass register. Never re-tested against the
full 48-note set, and no longer testable at all now that the script
doesn't report a fundamental — noted here in case fundamental detection
ever comes back.


6. CROSS-ANALYSIS ACROSS RECORDINGS (subprojects/statistic_from_audio/compare/)
---------------------------------------------------------------------------------
Added because analyzing one file at a time doesn't reveal trends across
the keyboard. compare/main.py uses the router's multi-select menu
(section 1) to pick any number of recordings, then asks which analysis
to run -- Amplitude, Harmonics, or Both -- and lays out each selected
recording's own plot(s) side by side (one row per recording, sorted by
pitch when the filename ends in a note name; columns = the analysis
type(s) picked), the same visuals amplitude/main.py and harmonics/
main.py produce individually, just all on one page instead of one file
at a time. A plain printed table (attack, decay, brightness start/end
per recording) prints below the plots -- not another graph.

UPDATE (2026-08-27): originally this reduced everything to two
aggregate trend-line plots (attack/decay vs. pitch, brightness vs.
pitch) plus a Pearson-correlation summary. Replaced entirely at the
user's request -- they wanted to actually SEE each recording's detailed
plot side by side (matching what the individual scripts show), not just
a pitch-vs-metric reduction, with the numbers as a plain table instead
of a third graph. The correlation math was cut along with the trend
plots since there was no natural place for it in the new layout; the
real finding it produced (below) is still worth keeping as project
history even though the tool that made it no longer exists in that
form.

COOL THING: this is the first script in the project that reuses the
other two scripts' *analysis logic* (attack/decay math, brightness/STFT
math) without reusing their *code* directly -- copied the functions in
rather than importing across sibling subproject folders, to keep
compare/ self-contained the same way every other subproject folder is
(matches the project's established one-folder-one-script pattern rather
than introducing cross-folder coupling).

REAL RESULT FROM THE RETIRED CORRELATION VERSION, run against all 48
notes (kept as history, not reproducible in the current UI): pitch vs.
decay time correlates
at -0.78 (strong) -- higher notes decay faster, matching known piano
physics and matching what showed up note-by-note earlier (section 5's
6.6s-vs-1.5s spread). Pitch vs. brightness change correlates at only
+0.06 (essentially no linear trend) -- whether a note brightens a lot or
a little over its duration does NOT depend much on how high or low it
is, at least across octaves 2-5 mezzo-forte. That's a genuine finding
from the tool, not an assumption baked into it.

BUG CAUGHT WHILE BUILDING THIS: the SNR-gated brightness code (see
section 2) threw a "divide by zero in log10" warning on some files --
a frame with exactly zero energy (pure digital silence before the
attack) produced log10(0). Harmless in effect (just becomes -inf, still
correctly below any real threshold) but noisy. Fixed by flooring
frame energy at a tiny epsilon before the divide, in both
harmonics/main.py and compare/main.py.


THINGS WORTH REMEMBERING GOING FORWARD
-------------------------------------------
- Piano notes: struck/decaying, no sustain plateau, slightly inharmonic
  overtones. Both analysis scripts are already tuned around this.
- The router's plain-menu fallback under Git Bash/MSYS isn't cosmetic —
  it's a hang fix. Don't remove that check.
- harmonics/main.py no longer does fundamental/note detection at all
  (removed on request) -- it's timbre-over-time (spectrogram + spectral
  centroid) now. Its noise-floor SNR gate (15dB above the pre-onset
  floor) is load-bearing, not decorative -- without it, brightness
  readings are dominated by noise as the note fades, not the real
  timbre. Don't lower that threshold without re-checking against real
  notes the way section 2's history describes.
- Pedal/polyphonic resonance (the MAESTRO round's failure mode) is
  explicitly out of scope for this project's goal.
- Weak-fundamental octave errors on low bass notes (found on
  piano_single_C2.wav / piano_single_G2.wav back when harmonics/main.py
  did fundamental detection) is now moot -- that code path is gone. Only
  relevant again if fundamental/note detection gets added back somewhere.
- Kaggle datasets need an API token this environment doesn't have and
  can't obtain interactively — don't assume Kaggle URLs are fetchable
  the way plain HTTPS/GCS ones are. University of Iowa's sample archive
  (theremin.music.uiowa.edu) needs no login and has full chromatic
  coverage per instrument/dynamic -- default here if more notes/octaves
  or other instruments are ever needed.
- compare/main.py's pitch-sorting depends on filenames ending in a note
  name (regex looks for e.g. "C4", "Db5" at the very end of the stem).
  Files that don't match that pattern still get compared, just sorted
  arbitrarily (sort_key falls back to 0) -- fine for now since every
  file in Sample Recordings/ follows the naming convention, but worth
  fixing if a differently-named dataset gets added later.

REORGANIZATION: the two single-recording analyses got grouped into their

NEW SUBPROJECT -- csv_export/: batch-runs the same attack/decay +

sweep pp/mf/ff and all 48 notes in one run. Synced to all four _shared.py
copies (single_note/amplitude, single_note/harmonics, compare, csv_export)
per the established "keep them identical" convention, even though only
csv_export currently calls select_folder().

Verified end-to-end (headless, mocked choose): ran csv_export against all
of Sample Recordings/, all 144 files processed with zero failures, wrote
144 rows to Results/Sample_Recordings_<timestamp>.csv. Spot-checked rows
looked sane (e.g. piano_single_A2.wav in ff: attack 0.64s, decay 5.35s,
brightness 875->1167 Hz). Results/ is NOT gitignored (unlike the .wav
files) -- CSVs are the actual analysis output the user wants to keep and
work with later, not disposable test data.

FOLLOW-UP (same day): user noticed many pp rows had blank brightness
columns and asked why. Root cause: the 15dB-above-noise-floor SNR gate
(same one harmonics/compare use, deliberately not loosened -- see section
6's "load-bearing" note) requires 3+ trusted STFT frames to fit a
brightness trend at all; pp is the quietest dynamic by definition, so it's
the one most likely to never clear that bar across the whole recording,
especially in the bass (less energy per frame than treble). Confirmed by
direct measurement: pp/piano_single_A2.wav's max SNR across the whole file
never exceeds 11.6dB, 0/260 frames trusted -> blank. pp/piano_single_B2.wav
barely clears it, 6/260 trusted -> a value, but a thin one.

Fix (not loosening the threshold, which stays deliberately strict): added
two columns, brightness_frames_trusted and brightness_frames_total, so a
blank or thin brightness reading is visible as such instead of looking
identical to a solid one. Re-verified against the real 144-file set after
the change -- pp/A2 shows 0/260 (blank, as expected), pp/B2 shows 6/260
(present but marginal), ff/A2 shows 200/260 (solid). Important for the
regression work ahead: brightness being unmeasurable is NOT missing-at-
random -- it's correlated with the low-force end of exactly the variable
being studied, so blank rows shouldn't just be dropped without accounting
for that bias (e.g. bass notes at pp will be systematically underrepresented
in any brightness-vs-force fit unless this is handled deliberately).


8. TREND-FINDING SUBPROJECT: Analysis/ (2026-08-29, same day)
-----------------------------------------------------------------------
User asked for a new subproject to actually look at the CSV data for
trends -- explicitly named "Analysis". Design choice made and acted on
without a separate confirmation round-trip (user had already committed to
the folder): one figure, three side-by-side subplots (attack time, decay
time, brightness change %), each plotting the metric against dynamic/force
level. Each note gets its own thin line connecting its available pp/mf/ff
points (colored by octave via a viridis colormap, so register effects are
visible at a glance), plus a bold black dashed linear fit line and printed
Pearson r per metric -- a first-pass numeric "equation" (y = slope*x +
intercept) for how each property scales with force, which is the user's
stated end goal. This is deliberately the "aggregate trend" style that got
retired from compare/ earlier (section 6) -- that retirement was about
compare/'s per-recording-detail purpose, not a rule against trend plots in
general; Analysis/ is a dedicated tool for exactly the aggregate-trend
case compare/ was pulled away from.

Mechanics: select_csv() lists Results/*.csv sorted newest-first via the
router's own choose() (auto-picks if only one exists), requires 2+ distinct
"group" values in the CSV to plot at all (single-dynamic CSVs get a clear
message instead of a meaningless single-point "trend"). Dynamic ordering
reuses the same pp<mf<ff DYNAMIC_ORDER lookup as compare/main.py (copied
in, self-contained per subproject as usual). Missing values (e.g. blank
brightness cells from the SNR gate) are skipped per-note rather than
crashing or zero-filling -- a note needs 2+ valid points to draw a line at
all. No _shared.py needed for this one -- it never touches Recordings/,
only Results/, so it just inlines _find_project_root() and imports choose()
directly from the router.

Verified against the real 144-row export (regenerated fresh since Results/
had been cleaned up after prior testing): 3 groups found (pp, mf, ff);
Attack time: n=144, r=+0.42 (attack gets slightly slower/later at higher
force); Decay time: n=144, r=-0.59 (decays meaningfully faster at higher
force -- the strongest relationship in the dataset); Brightness change:
n=110 (34 rows dropped, consistent with section 7's SNR-gate gaps), r=-0.10
(weak/near-flat). Sanity-checked the fit line itself wasn't a rendering
bug -- pulled its raw Line2D data (xdata=[0,2], ydata=[0.373, 0.559] for
attack time) to confirm it's a genuine straight 2-point fit; what looked
like a kink in the rendered PNG was just visual crowding from ~48 overlapping
thin note-lines, not an actual bend in the trend line.

Caveat carried over from section 6/7: pp/mf/ff are still only 3 categorical
force levels, so "linear fit" here is a straight line through group means,
not a real regression against a continuous force variable -- good for
spotting direction and rough magnitude, not a substitute for MAPS-style
continuous-velocity data if the user wants to fit a precise equation later.
